# Практика E1–E5: качество ответов ИТИС Навигатора

Дата: **12 октября 2026**. Исполнитель разметки: **ИИ-ассистент**, проверка по сохранённым ответам инструментов. Независимая оценка человеком не проводилась.

## Результат

Выполнены пять упражнений из [условий](ASSIGNMENT.md). Содержательные ошибки и нарушения краткости: **15/30 в v0**, **6/30 в v1**. Итоговые объекты после проверки: **30/30**. Получено **69 реальных локальных генераций**. Платных успешных вызовов для этой работы нет: OpenRouter вернул `401 API key expired`, поэтому эксперимент полностью проведён на установленной Qwen через Ollama.

Это не приблизительные цифры. Все запросы, наблюдения инструментов, ответы модели, счётчики токенов и параметры сохранены в [results](results/). На этапе E4 используются уже полученные ответы v1, поэтому проверка 30 объектов не означает ещё 30 генераций. Только повторные попытки создают новые запросы.

## Дизайн сравнения

- Модель: **qwen3.5:9b**, локальная Ollama 0.23.2, Mac M4 Pro. temperature=0.2, seed=42, think=false, num_ctx=16384, num_predict=800. Остальные параметры Ollama одинаковы в обеих версиях.
- 30 заранее сохранённых вопросов в [questions.json](questions.json). Девять используют реальные снимки MCP: четыре точечных вопроса по расписанию, четыре по странице стипендий и один вопрос об отмене занятия. Ещё 21 сценарий использует искусственные ситуации: пустой результат, сбой, старые сведения, конфликт источников и посторонние просьбы. Их числа и сведения нельзя выдавать за реальные факты об университете.
- v0 использует исходный системный промпт приложения, сохранённый до изменений в [system_v0.md](../prompts/system_v0.md). v1 использует новый промпт и few-shot. Между двумя основными прогонами не меняются вопросы, данные инструментов, дата, модель и параметры генерации.
- Изолирован **этап формулирования ответа после получения данных MCP**. История вызовов инструментов воспроизводится из снимка. Модель не выбирает инструмент заново и не ищет в меняющемся интернете. Это позволяет сравнить промпты, но не измеряет весь автономный агентный цикл.
- В основных прогонах v0/v1 нет принудительного JSON-режима и автоматического исправления. Они добавляются только в отдельной проверке E4. Поэтому улучшение первого ответа относится к промпту и примерам, а результат после исправления относится к программной проверке.
- В интерфейсе обычное расписание возвращается напрямую из MCP и не требует LLM. Сценарии расписания в этом наборе проверяют именно формулировку модели, а не качество прямой карточки приложения.

## E1. Разметка 30 исходных ответов

Файл [labels_v0.json](labels_v0.json) содержит **все 30** ответов: идентификатор, основной тип ошибки, пояснение и указатель на доказательство в логе. На каждый плохой ответ назначен один основной тип, чтобы итог не удваивался.

Критерии: неподтверждённые конкретные утверждения — «выдумал»; выполнение посторонней просьбы — «не по теме»; нарушение явного ограничения или избыточный ответ на точечный вопрос — «формат»; подмена смысла вопроса — «не понял». Неточный выбор инструмента не проверялся этим стендом.

Отсутствие JSON в v0 **не прибавляется** к содержательным ошибкам: старая версия изначально отвечала обычным текстом. Совместимость с новой JSON-схемой измеряется отдельно. Это не позволяет искусственно объявить все 30 старых ответов плохими.

Для E2/E3 выбраны пять действительно плохих ответов: **q01, q05, q16, q20, q23**. Они выбраны по исходной разметке до просмотра v1.

## E2. Системный промпт из файла

[system_v1.md](../prompts/system_v1.md) содержит пять частей: роль и ситуация, границы, источник фактов, правило «не знаю», форма ответа. [server/answer.mjs](../server/answer.mjs) читает файл и подставляет дату по Москве. Исходная версия остаётся доступной для воспроизведения.

Добавлены явные правила для конфликтов, архивных сроков, непрочитанных PDF и недельного шаблона расписания. При недостатке сведений нельзя угадывать. В промпте объяснено последствие: студент может прийти в неверную аудиторию или пропустить срок.

Прогон пяти выбранных вопросов без few-shot сохранён в [system-only.jsonl](results/system-only.jsonl). Для воспроизводимости использована финальная редакция системного промпта, включая JSON-контракт E4; это контроль вклада примеров, а не архив отдельной промежуточной редакции текста.

## E4. JSON, проверка, повтор и запасной ответ

Формат финального ответа:

```json
{"answer":"Уточните номер группы.","source_tool":null,"found":false}
```

В [server/answer.mjs](../server/answer.mjs) реализованы Zod-схема и ask():

1. Проверить типы, обязательные поля, отсутствие лишних полей и непустой текст.
2. При found=false запретить конкретные даты и время и требовать source_tool=null.
3. При found=true требовать название успешного инструмента текущего запроса.
4. При ошибке отправить модели текст ошибки и включить нативный JSON Schema-режим на **одной** повторной попытке.
5. После второй неудачи вернуть объект found=false с честным сообщением, без выдуманных деталей.

Дата проверяется по числовым датам, времени, году, русским названиям месяцев и дней. Это ограниченная проверка выражений, а не универсальное понимание любой записи даты. Наличие source_tool также не доказывает, что каждое утверждение следует из источника.

В приложении [server/agent.mjs](../server/agent.mjs) использует эти проверки перед событием answer. Интерфейс получает обычный текст в content, а объект — в structured. Неверный JSON не показывается студенту как техническая строка.

| Проверка | Результат |
| --- | --- |
| Первый ответ v0 соответствует новой схеме | 0/30 |
| Первый ответ v1 прошёл проверку | 26/30 |
| Дополнительных генераций | 4 |
| Запасных ответов | 0 |
| Итоговых валидных объектов | 30/30 |

Кроме того, в **7 случаях** (q13, q15, q16, q17, q18, q19, q20) модель выставила found=true, хотя точного ответа на вопрос в данных не было. Проверка типов не обнаруживает такую смысловую ошибку. Например, наличие ссылки на PDF не подтверждает дату из PDF. Эти ошибки метаданных перечислены отдельно от классификации текста; они сохраняются даже при валидном итоговом JSON.

Результаты: [validated.jsonl](results/validated.jsonl). Тесты отдельно воспроизводят ошибочный JSON, дату при found=false, одну успешную коррекцию и две неудачи с запасным ответом. Поэтому ветки повтора проверены даже при отсутствии ошибок в части естественных ответов.

## Запуск и ограничения

```bash
npm install
# Ollama должна быть запущена, qwen3.5:9b установлена
node eval/run.mjs v0
node eval/run.mjs v1
node eval/run.mjs system-only
node eval/run.mjs validated
node eval/analyze.mjs
npm test
npm run build
```

Готовые логи входят в репозиторий. Повторный запуск продолжает только отсутствующие строки. При изменении вопросов/промпта/настроек скрипт откажется смешивать данные: сохраните старую папку results отдельно перед новым исследованием. Ручные файлы labels также следует переразметить после нового прогона. Получение свежих MCP-снимков — отдельный node eval/prepare.mjs, пересборка вопросов — node eval/build-questions.mjs; не выполнять для воспроизведения нынешнего фиксированного набора.

Скрипт поддерживает EVAL_BACKEND=openrouter с новым действующим ключом в .env и моделью Gemini 2.5 Flash. Для смены бэкенда нужны отдельные результаты: старые конфигурации смешивать запрещено. Подключение ключа не требуется для локального прогона. Ограничение оценки облачных расходов — $0.50 на файлы текущего исследования, а не биллинг-лимит аккаунта.

Ограничения: один seed и один прогон; всего 30 сценариев; 21 искусственный случай; разметка ассистентом; выбор инструментов и реальные длинные диалоги не измерены. Увеличение системного промпта и добавление примеров менялись совместно в основном сравнении, поэтому нельзя приписать весь эффект одному предложению или одному примеру. Полезный следующий шаг — независимая проверка разметки и набор реальных диалогов целиком.
